## [1.6.0] - 2026-10-16

### Added

- Add a Codex adapter with conservative MCP configuration, packaged workflow skills, managed AGENTS.md instructions, diagnostics and ownership-aware uninstall. (integrations)
- Add integration lifecycle commands and read-only doctor diagnostics, including configured MCP interpreters and editable-source dependency drift; include production-entrypoint cross-client tests. (integrations)
- Add an opt-in isolated Codex benchmark with three controlled retrieval arms, persisted model-step usage, exact payload checks and offline validity tests; distinguish exploratory totals from attributable evidence. (benchmarks)
- Add native Codex hook event normalization and shared append-only task mirroring, preserving Claude behavior, real actor identity and worktree boundaries; distinguish installed definitions from client trust. (integrations)
- Give items an optional short label (short_title, up to 50 characters, refused rather than truncated) that says in a few words what an item is about; set it with create_item/update_item (update_item(short_title="__clear__") removes it), the promote tools, and the CLI flags add --short-title/-S and update --short-title; dct show, dct list (Label column) and the web dashboard display it. (items)
- Show a label next to every item number in the context snapshot, review_sprint, list_items_in_sprint, gates and sprint checkpoints: item rows carry short_title, rows that refer to an item carry item_short_title (the short label, or the title shortened to 50 characters when no label is set); create_item and update_item acknowledgements echo short_title so a caller can tell the value was stored. (mcp)
- Record the git branch and worktree a changelog entry was written on: add_changelog and clog add take branch/worktree (clients should pass them, since the MCP server's directory is the session start directory); without them the value is detected only when the checkout lies inside the project path, and branch_source says who supplied it. list_changelog, count_unreleased_changelog, clog list and clog count filter by branch, worktree and include_unbranched; unfiltered reads are unchanged. Changelog rows also carry the related item's label. (changelog)
- release_changelog and clog release can stamp an explicit set of entries (entry_ids / --entries) or only the version (entry_ids=[] / --no-entries); the set is validated strictly and applied all or nothing, a repeated release of the same set is a no-op, a version lower than the current one is refused, a bump is computed inside the release transaction, and the answer reports the mode, the version and which entries were stamped or already released. (changelog)
- Correct or withdraw an unreleased changelog entry with update_changelog / delete_changelog (MCP) and clog update / clog delete (CLI); released entries stay unchanged as history, and deletion is a soft delete. (changelog)
- Keep a durable record of every release (version, exact entry set, pinned candidate commit, checkout, progress) written in the same transaction as the stamp; an interrupted release is finished with `dct release resume`, which skips effects that already exist and stops on any contradiction, and a repeated release with the same set returns its record instead of stamping again. get_release (CLI `clog release-status`) reads the record; advance_release (CLI `clog release-advance`) reports the progress of a release the project's own tool performs. (changelog)
- Add `dct release`, one layered release workflow behind /release. `plan` and `clog candidates` show, read-only and with `--json`, which unreleased entries the candidate commit proves through `Changelog:` trailers (reverts, squash merges and the nearest release tag are accounted for); `attest` records the owner's confirmation of unproven entries as an empty commit; `prepare` runs the version-sync script once in an isolated checkout of the candidate and stores the exact files it would change as a proposal; `apply` stamps, writes the changelog and the approved files, commits, tags and pushes — only for the plan and proposal digests the owner approved; `resume` finishes an interrupted release on the stored consent; `abandon` and `status` complete the set. `clog release` is an alias of apply and needs the same approval. (release)
- A release is pushed only where the owner approved: a new release in git needs the complete `--push-remote`, `--push-branch` and `--push-url` shown by prepare, or an explicit `--no-push`. The push goes to that URL with explicit refspecs, never follows tags or submodules, refuses a URL that git could rewrite or read as a remote name, and is verified on the destination before the release is recorded as pushed; a failed push leaves the release tagged and `resume` retries only the push. (release)
- Record who performs a project's releases with `dct project release-executor dct|own`: a project with its own release tool keeps its effects, uses the shared plan and reports progress through get_release / advance_release / abandon_release with tag and push proof, and dct's own effects refuse to touch its releases; a release keeps the executor it was stamped with even when the setting changes later. (release)
- Record releases made before the release ledger without stamping them again: `dct release reconstruct` verifies the release commit, its tag, the changelog history against the parent commit and the version files, and records the stage that is proven; `dct release takeover` lets dct finish an old or MCP-stamped release after the owner approves a consent derived from the verified artifacts; `dct release version-files` shows and confirms the project's version-file contract. (release)
- `dct db upgrade` creates or upgrades the database schema explicitly; the read-only commands (`dct release plan`, `dct clog candidates`, `dct release status` and the reconstruct preview) never create or change a database and say when an upgrade is needed. (cli)
- dct finds a project's changelog file instead of assuming changelog.md: a tracked CHANGELOG, CHANGES, HISTORY, NEWS or RELEASES file in any letter case is detected, several candidates are listed for the owner to choose with `dct project changelog-path`, which now records a deliberate choice (also exactly changelog.md; `--detect` returns to detection), and a changelog in another format than Markdown is never written into — the plan says so and offers a rewrite, an explicit Markdown path or turning dct's changelog file off. A historical release is judged by its own commit, not by today's changelog name. (release)
- `dct release plan` proposes the version (`version.suggested`: bump, target, reason, alternatives, whether the proposal is safe) from the categories of the entries that go in: fixes only give a patch, additions a minor, removals a major from 1.0 on; a 0.x project is never pushed to 1.0.0; a version a tag, a record or released history already holds is skipped; a project without a version and without a tag starts at 0.1.0. The suggestion sits outside the plan snapshot, so the plan digest is unchanged (plan schema 5). (release)
- `dct release prepare --preview` shows the whole release on one screen before anything is committed — the suggested version, the entries that go in and those that wait, the changelog section, the version files, the push target and, when the tree is dirty, the work-in-progress commit dct will make — and returns a consent digest per shown variant (the plain release and "release with all N"); `--discard-preview` drops it. `dct release apply --consent C --confirm` releases exactly the approved screen: it makes the work-in-progress and attestation commits through the repository's hooks, checks the content against the screen before and after them, refuses an unknown commit identity, a hook that changes files, an index-only difference or a lost recorded commit before anything is published, and a re-run finishes what an interrupted run already made. `dct release plan` reports the stored preview as `pending_consent`. (release)
- Commit-trailer preferences are stored with the project (`Co-Authored-By`, a session link; not answered yet is different from a stored "no"): /dct-init asks once, `dct project trailers <slug> --co-authored-by on|off --session-link on|off` changes them, `list_projects` shows them, and /commit applies them without asking — a project's own rules forbidding a trailer still win. (projects)
- `dct clog candidates --json` marks changed files whose path looks like a secret (`secret_like`, with a quoted command to unstage it), using the same path check as the release preview; /commit never offers such a file for staging and stops when one is already staged, without touching your index. It is a path check, not a scan of file contents. (release)
- `dct project version-sync-script <slug> [--kind FILE]` writes a project's scripts/dct-version-sync.sh from a generic template shipped in the package (every block commented, portable — no `sed -i`, no temporary file — and keeps the file's mode), with the block of the detected version file switched on; it never overwrites an existing script. /dct-init no longer copies dct's own release script, which edited dct/__init__.py and was missing from installs from PyPI (projects)
- `dct show N` lists the item's checkpoints with id, kind, status and full text — the full list the gate refusal points at (cli)

- The commit changelog guard and the Stop reminder count the unreleased entries of the current branch (plus entries without a branch) instead of the whole project, fall back to the project count with an older dct, and the commit guard no longer blocks a commit when its own count fails; the Stop reminder still reminds in that case. (hooks)
- /commit records which changelog entries a commit contains as a "Changelog: <ids>" trailer, chosen against the final staged diff from the current branch's unreleased entries; /clog and the Codex clog workflow pass the branch and worktree they run in; /track, the Codex track workflow and dct-import always set a short label, and /track-list shows it. (skills)
- /release releases only the entries the candidate commit proves through Changelog trailers (previous release tag to the pinned candidate commit), as reported by `dct release plan`; before anything is stamped the owner attests, corrects, withdraws or keeps each unproven entry, a version-only release is asked about instead of stopping, and a release started in a git worktree uses that checkout: its plan, its version-sync script and its changelog file. (skills)
- Versions follow one contract: X.Y or X.Y.Z with an optional leading "v", which is removed before the version is stored; other formats are refused, releases never move current_version backwards, and a repeated release of an already released version changes nothing. (core)
- The release commands must run from a checkout of the project's repository (any linked worktree or monorepo subdirectory works; a nested or foreign repository does not). `clog release` is now an alias of `dct release apply`: it needs `--confirm`, the proposal digest from `dct release prepare` and the approved push target or `--no-push`, and `--no-entries` to release a version without changelog entries. The version-sync script no longer runs in it: it runs once, isolated, in `prepare`, and a failing script ends prepare with the script's exit code and nothing stamped. (cli)
- A release of a new version without changelog entries must be requested explicitly with entry_ids=[] (MCP) or --no-entries (CLI) on every path; release_changelog without entry_ids and with nothing unreleased now returns an error instead of silently setting the version. Repeating an existing release stays a no-op. (changelog)
- Release and attestation commits are created on the pinned candidate and published with a compare-and-swap, after the repository's commit hooks ran on exactly the approved tree; a hook that changes the content or the message stops the release before anything is published, and the user's own staging is never overwritten. The release workflow needs git 2.36 or newer and refuses before any effect on an older git. (release)
- One release operation runs per repository at a time: every mutating release command takes a repository-wide lock; the version-sync script, hooks and push run supervised in their own process group, are stopped on a timeout, Ctrl-C or SIGTERM, and their output is bounded; a process left over from a killed run makes the next operation refuse instead of running beside it. Git commands of the release workflow no longer have a controlling terminal, so an ssh key needs an agent and commit signing a non-terminal pinentry. (release)
- The release ledger keeps proof, not a status alone: a record stores the verified tag and the verified push, refuses progress when its entries, consent, proposal or proofs contradict each other, and refuses every write when two records claim the same version. MCP advance_release and abandon_release refuse releases that dct's local workflow executes (use `dct release resume` / `dct release abandon`); a serialization conflict ends a release command with exit code 75 and a report of what was already done, without an automatic retry. (release)
- Only a release gives a changelog entry its version: creating an entry with a version is refused (old history is imported through a separate path), a release compares the expected executor inside the same transaction as the stamp, and a pull-request number in a release's proof records whether git recognised it or a client declared it. (core)
- Support SQLAlchemy 2.1 next to 2.0.52 and newer: SQLite database URLs are built and parsed by SQLAlchemy itself, so a database path with URL metacharacters opens the same file on both lines; a path that cannot be expressed on the installed version is refused instead of opening another file. (dependencies)
- /release is one workflow from start to push: it routes from a single plan result (a new release or an unfinished one, dct or the project's own tool), commits work in progress in the same run once the owner agrees, shows the prepared files and the push target for approval, applies, pushes and reports; an interrupted release resumes on the stored consent without asking again, and an old release without a consent is finished through the takeover the owner approves. The fallback instructions follow the same steps and refusal table. (skills)

- A release no longer stops after the stamp because of its changelog file: every condition about the file that can be known beforehand — another letter case or name than the configured one, several candidate files, a path through a symlink, a file or a submodule, a file outside the project, a non-Markdown file, content that is not UTF-8 or already holds the version's section, a filter that would alter the composed text, a leftover local tag of the version, an existing index.lock — is refused by prepare and apply before anything is written, with a true next step; the changelog is written in the form a fresh checkout gives, so a CRLF file under text=auto releases again and again. - The git commands dct suggests for a changelog-file problem (rename, replace a link, check the file out again through its filters) quote every path they contain, so a name with spaces or shell characters pastes as one argument. (release)
- `dct release plan` says in advance whether `dct release resume` would refuse an unfinished release (`resume.blocked`, with the commands that restore the setting or abandon the record) — the same check resume runs; the /release skill no longer offers "finish" when it is known to fail. ### Fixed

- Invariant "terminal item status ↔ resolved_at set" — update_item(status="resolved"|"wont_fix") now sets resolved_at automatically, and update_item(status="open"|"in_progress") clears it on reopen. Previously only resolve_item() stamped the timestamp, leaving items resolved via update_item silently missing the audit field. Added TERMINAL_STATUSES / OPEN_STATUSES constants in core/items.py and 4 regression tests (update→resolved, update→wont_fix, reopen→open, reopen→in_progress) (core/items)
- Migration runner BOOLEAN default bug on PostgreSQL — ALTER TABLE ADD COLUMN in_current_sprint BOOLEAN NOT NULL DEFAULT 0 failed with DatatypeMismatch ('0' is INTEGER, not BOOLEAN). Fix: dialect-aware literal dispatch (`FALSE` for PostgreSQL, `0` for SQLite) applied to both column default and index predicate. Changed server_default on the SQLAlchemy column definition from `sa.text("0")` to `sa.false()` for portable CREATE TABLE on fresh PG DBs. Root cause: tests run against in-memory SQLite which is permissive; PG is strict. Added 9 regression tests in tests/test_migration.py including a dialect-literal lock-in test to prevent recurrence. (db)
- Migration runner partial-state healing — _apply_schema_updates() now checks each schema change (column present, index present) INDEPENDENTLY instead of treating a migration group as atomic. A prior failed migration that added the column but not its index was not healed on next run because the column check short-circuited the entire function. This mirrors the invariant-per-field rule from core/items.py (TERMINAL_STATUSES/resolved_at coupling). (db)
